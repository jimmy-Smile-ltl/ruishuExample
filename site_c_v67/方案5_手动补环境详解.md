# 方案 5 详解：手动补环境（纯 Node，无浏览器）

> 文件：`spider_manual_env.py` + `env/browser_envs.js`
> 实测：412 → 200 稳定，2.7-3.7s/次，无需任何浏览器/jsdom
> 日期：2026-08-15

---

## 一、核心思想

瑞数的挑战流程在浏览器里是这样的：

```
412 页面
  ├── meta 编码数据 (arg1)
  ├── $_ts 初始化脚本 (arg2)
  └── VM 解释器 JS (~304KB, ts_code)
        ↓ 执行
  动态生成二层代码 (~490KB) → eval 执行
        ↓
  环境检测 + 定时器阶段积累数据
        ↓
  计算 P-cookie → document.cookie → 自动重载 → 200
```

**补环境 = 在 Node 里伪造一个"够用"的浏览器环境，让这段 JS 完整跑完。**
不需要真实浏览器，不需要 jsdom —— 一个手工搭的假 window/document 就够。

---

## 二、整体流程

```python
# spider_manual_env.py
[1] curl_cffi GET 目标页 → 412 + O-cookie (Set-Cookie)
    提取: arg1 (meta content) | arg2 ($_ts 初始化脚本) | ts_code (VM JS)
[2] 三个占位符注入 env/browser_envs.js:
     arg1_content / "arg2_js" / "ts_code" → 拼接成完整 JS
    Node 执行 → VM 跑完 → P-cookie 落进 document.cookie
[3] 1.5s 后读 cookie → 同 session 带 O+P 请求 → 200
```

每个挑战的参数都是动态的（每次 412 的 meta/nsd/cd 都变），
所以**每轮都要重新拿 412 + 重新跑 Node**。

两个实现细节：

```python
# 读取回调里必须 process.exit(0) —— VM 的 setInterval 会挂住 Node 进程
env_js += '\n;setTimeout(function(){ console.log("COOKIE_START:" + get_cookie()'
env_js += ' + ":COOKIE_END"); process.exit(0); }, 1500);'
```

```python
# O-cookie 在 session 里 (Set-Cookie 自动收), P-cookie 从 Node 输出解析后合并
for part in p_cookie.split(";"):
    if "=" in part and not part.startswith(("path=", "expires=", ...)):
        k, _, v = part.partition("=")
        session.cookies.set(k.strip(), v.strip())
```

## 三、browser_envs.js 的分层结构

| 层 | 内容 | 作用 |
|---|------|------|
| 0 | 定时器 | **异步 + try/catch**（最关键） |
| 1 | `Function.prototype.toString` 保护 | 反"检测被 hook" |
| 2 | `window = global` 融合 | VM 用裸名访问 window 属性 |
| 3 | DOM 对象 | document/meta/div/script 元素 stub |
| 4 | navigator/location/screen/history | 常规浏览器对象 |
| 5 | Canvas 指纹 | 固定 toDataURL 值 |
| 6 | document.all | HTMLAllCollection 特殊语义 |
| 7 | cookie 存取 | P-cookie 的落点 |

## 四、四个关键坑（本次实战攻克的）

### 坑 1：定时器必须异步 ★根因

原模板把 `setTimeout/setInterval` **同步 flush**（注册立即执行）：

```js
// ❌ 原版：同步执行
setTimeout = function (v1, v2) { v1() }

// ✅ 修复：异步 + try/catch
setTimeout = function (v1, v2) {
    return setTimeout_(function () {
        try { v1(); } catch (e) {}
    }, v2)
}
```

**后果**：同步 flush 时 VM 的 timer 驱动阶段被跳过，basearr 少 30 字节
（P 257 vs 343 chars），服务端 412 拒收。异步后 cookie **1 秒就绪**。

**try/catch 的作用**：timer 阶段会对 `undefined` 设 `.id`（DOM stub 不全导致），
但不影响 cookie 完整性 —— 吞掉错误让阶段继续跑。
这正是 sdenv 的 jsdom 环境里"缺失 API 不崩溃"的同款技巧。

### 坑 2：Location 必须与目标站一致

原模板硬编码了**另一个网站**的 URL（脚本上一个适配站的残留）：

```js
// ❌ 原版（上一个适配站残留的 URL）
"href": "<旧站URL>"
// ✅ 修复（env/browser_envs.js 顶部 TARGET_URL 常量, base64 解码后使用:
//    aHR0cHM6Ly9zdWdoLnN6dS5lZHUuY24vSHRtbC9OZXdzL01haW4vMTAyLmh0bWw=）
"href": TARGET_URL
```

**原因**：`hostname` 会被编进 basearr 再加密进 cookie ——
服务端解密后校验 cookie 内嵌的 hostname 与请求的 host 是否一致，不一致直接拒。

### 坑 3：document.all 的特殊语义

真实浏览器的 `document.all` 是个奇葩：
`typeof document.all === 'undefined'` 但值却可用（[[IsHTMLDDA]]）。
VM 会遍历它的内容：

```js
myObject.all.push(meta, script1, script2)   // 内容 = 页面元素
myObject.all.toString = function () {
    return "[object HTMLAllCollection]"     // 正确字符串化
}
```

### 坑 4：函数 toString 保护

VM 检测 `setTimeout.toString()` 是否还是 `[native code]`（判断是否被 hook）。
模板用 `Symbol` 存原始字符串 + 覆写 `Function.prototype.toString` 来对抗：

```js
const $toString = Function.toString;
const myFunction_toString_symbol = Symbol(...);
delete Function.prototype['toString'];
set_native(Function.prototype, "toString", mytoString);  // 返回伪造的 native 串
```

## 五、为什么环境可以这么"假" —— 访问日志证据

给 document/navigator/location/screen/history 包 Proxy 记录了 VM 的全部读取，发现：

**VM 生成 cookie 时只读这些**：
- `document.all` / `document.cookie` / 几个 DOM 方法
- `location.*`（href/hostname/pathname...）
- webdriver 检测属性（`__driver_evaluate` 等，正确返回 undefined）

**完全不读**：navigator、screen、canvas！

这解释了为什么 sdenv 的 `screen 0x0`、`Mac UA` 都能过 ——
**服务端只校验 cookie 内部一致性**（加密结构 + hostname），不校验指纹值真实性。

**补环境的及格线比想象的低得多**：VM 在两种环境走了不同分支，
差的只是 timer 阶段那 30 字节。

## 六、可复用的调试方法论

### 1. 同轮结构对比（定位差异在哪一段）

同一轮挑战里，用 rs-reverse 的 Feistel 解密器解密两个环境生成的 cookie：

| 字段 | 通过的环境 | 失败的环境 |
|------|-----------|-----------|
| nextarr 总长 | 199 | 169 |
| basearrEncrypt | 134 字节 | 104 字节 |

→ 精确定位：差的是加密后的 basearr（30 字节）。

### 2. Proxy 访问日志（找分支因素）

包装所有环境对象，记录 VM 读了什么、返回了什么：

```js
function _wrapLog(name, obj) {
    return new Proxy(obj, {
        get(t, k) {
            console.log("[ENV-DIFF]", name + "." + String(k), "->", String(t[k]).slice(0, 50));
            return t[k];
        }
    });
}
```

与"通过"的环境逐项对比返回值的差异。

### 3. 二分定位（验证假设）

把差异项逐个改，看 cookie 长度变不变 —— 变了就找到了分支因素。
没变就排除（本次就排除了 location/document.all 长度/visibilityState 等 5 项，
最终锁定定时器）。

## 七、移植到其他瑞数站的要点

1. **改 Location**（最容易忘的，后果是 cookie 内部 hostname 不符被拒）
2. **先跑通再看 cookie 长度** —— 长度对不上说明有分支差异，上访问日志
3. **timer 阶段异步**是默认要开的（同步 flush 只在个别老版本 VM 可行）
4. 每个站的 VM 读的环境项不同（有的站会读 canvas/navigator），
   以访问日志实测为准，别照抄别的站的环境清单
5. Node 脚本尾部必须 `process.exit(0)`
