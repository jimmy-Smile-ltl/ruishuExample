# 站点D 瑞数纯算法路线攻克思路（2026-08-15）

> 目标：不跑浏览器、不做环境模拟，纯还原算法生成有效瑞数 P-cookie。
> 结果：257 字符纯算 cookie 通过服务器验证（200），复验 200×2，错误名对照 412。

---

## 一、问题定义

[pysunday/rs-reverse](https://github.com/pysunday/rs-reverse) 已完整逆向瑞数加密体系的**外层**：

```
cookie = '0' + b64(Feistel-CBC([uuid(4) + nextarr], keys[16] + time))
uuid   = CRC32(nextarr)                    ← 解密正确性校验
nextarr = [r2mkaTime(4) + startTime(4) + keys2(48) + hasDebug(1) + basearrEncrypt]
```

外层 Feistel-CBC 通用，**内层 basearr 每站不同** —— 框架用"适配器"机制
（`src/handler/basearr/`，按加密后长度分类：len103/123/127/133/157/163/166）。

站点D 站点换新 VM 后，两个问题叠加：

1. **makecookie 任务执行崩溃**（约 2/3 挑战轮次）
2. **生成的 cookie 被服务器 412 拒**（即使生成成功）

---

## 二、诊断一：任务执行崩溃（变体 B 轮次）

**现象**：`TypeError: _$no is not a function` / `_$d$ is not a function`，
失败任务位置恒为 `0>one>23-25 / 24-26 / 25-27`（偏移任务 U14124020），
但每轮挑战的内部变量名轮换（`_$no`→`_$d$`→`_$l_`…）。

**定位手段**（关键教训：静态分析动态代码 800+ 函数会淹死，必须抓运行时）：

1. **运行时抓值**：makecode 保存的产物 vm-dynamic.js(319543) ≠ Coder 运行时
   实际执行的 code(317610) —— 调试必须 hook 运行时 codemap
2. **REG-DUMP 钩子**：在 runTask.js 失败 catch 里输出全寄存器快照
   （eval 的 var 会泄漏到外层作用域，catch 里可直接读）：

```
[REG-DUMP] _$d$ = obj(arr243)   ← 被当函数调用的寄存器，装着 cp2 数组
           _$h4 = 58            ← cp2[58] 是数字，真实 VM 里是函数
```

3. **根因**：`tscp.js` 一行 `parse($_ts.cp[2]).map(Number)` 把 cp2 表里
   所有**函数项**强转成数字。框架作者假设"偏移任务只取 cp2 数字项"
   （源码注释明说），站点D 新 VM 打破假设。

**处理**：未修根因，采用**变体轮换重试**绕行（约 1/3 轮次可过任务执行）。
每轮挑战的 VM 内容不同，重试 = 换一个新挑战轮。

---

## 三、诊断二：cookie 生成成功但被 412 拒

这才是核心问题。用**同轮对比法**测出真实结构：

```
① curl_cffi 拿 412 → 保存同轮三件套: 412.html + ts.json(hasDebug) + vm.js + O-cookie
② sdenv jsdomFromText 在同一份 412.html 上跑真 VM → 真实 P-cookie (343 chars)
③ rs-reverse makecookie 同轮材料 → 生成 P-cookie (257 chars)
④ 用户 inner_decrypt_search hook 解密真实 cookie 外层 → 实测结构
```

**实测数据**（关键突破口）：

```
[HOOK] P len: 343  nextarr: 225  hd: 128(hasDebug位)  basearrLen: 160  basearrEncrypt: 160
```

**真实 basearrEncrypt = 160** —— 而框架 7 个适配器是 103/123/127/133/157/163/166，
**一个都不对**。这就是 412 的直接原因。

**假设**：新 VM 的 basearr 结构与 len103 同构（同样的 9 段 numarrJoin 布局），
只是某个段更长：103→160 差 57，最可疑的是随机字节段
（len103 模板里 `execRandomByNumber(98)` → 新 VM 疑为 155 = 98+57）。

---

## 四、修复与验证

1. **len160 适配器**：复制 len103 结构，随机字节段 98→155，`lens: 160`
2. **验证循环**：O+P 组合 → curl_cffi 请求 → 服务器当 oracle
3. **T/P 名轮换**：cookie 名后缀按挑战轮次在 T/P 间轮换（实测发现），
   验证时两种名都试

**结果**：

```
[第1轮] ✅ <随机名>P 通过 (200, 25128b, 257-char P-cookie)
复验 200×2 + 错误名对照 412（名特异性确认）
```

**意外收获**：生成的 cookie 只有 257 chars（真实 343），服务器**照样接受**。
→ 服务器校验的是 cookie 的**自洽性**（CRC32 校验 + Feistel 密钥绑定 +
basearr 结构字段合法），不卡精确长度。适配器有容错空间。

---

## 五、工程化落点

| 问题 | 对策 |
|------|------|
| VM 变体轮换（2/3 轮任务崩溃） | prep 新挑战轮重试（实测通常 1-3 轮内成功） |
| cookie 名 T/P 轮换 | 两种名都试 |
| 首次请求偶发 412（额外挑战轮） | 会话自动吸收新 O-cookie 后重试 |
| hasDebug 变体 | ts.json 强制 `hasDebug: true`（实测 hd 位 0x80） |

---

## 六、方法论总结（可迁移到其他瑞数站）

1. **同轮对比**：真实样本与生成样本必须来自同一个 412 挑战
   （ts/vm/O-cookie/真实P 四件套同源），否则对比结果全是噪声
2. **运行时抓值 > 静态分析**：VM 动态代码 800+ 函数、每轮换名，
   hook 寄存器快照是唯一有效路径
3. **服务器当 oracle**：适配器参数空间大时不要穷举逆向，
   循环测试 + 服务器 200/412 反馈最快收敛
4. **先量真实结构再改模板**：真实 basearrEncrypt 长度是适配器的第一线索
   （本例 160 直接锁定方向）
5. **复用轮子**：外层解密器（Feistel 逆向）、hook 框架、适配器模板
   全部复用 rs-reverse 生态 + 项目内已有成果

## 附：手写补环境 v3 的窗口定位与稳定化（2026-08-15 晚）

### 问题

手写补环境 cookie 同轮内 3/8 稳定通过——pass/fail 由什么决定？

### 定位方法：同轮多跑 + 解密对比

```
变体 A 轮 (rs-reverse 能出 keys) → 同轮跑 harness 8 次 (每次校准值不同)
→ 每个 cookie 验证 (200 双复验) → 分 pass/fail 组
→ 解密对比: 前 16 字节完全相同 (uuid 段), 差异从块 1 开始
→ 判别器 = 块 1 的 execNumberByTime (时间敏感校准值)
   后续 155 随机字节是组内噪声, 非判别器
```

关键认知：**校准值由 VM 定时循环计数产生，每次运行天然浮动**——
WAF 窗口宽的站（pro8）全部落在窗口内（20/20）；
窗口窄的站（站点D）在边缘摇摆（~50%）。

### 稳定化 v2：同轮多跑 + 双复验

校准值每次运行不同 → 同轮重跑 = 换彩票：

```
同轮最多 6 跑 × 每跑验证 (200 需复验 2 次防假通过)
→ 10/10 轮稳定通过, 平均 2.3 跑/轮
```

零依赖路线由此完全可用。站点选择逻辑：WAF 窗口宽 → 单跑即可（pro8）；
窗口窄 → 多跑收敛（站点D v2）。
